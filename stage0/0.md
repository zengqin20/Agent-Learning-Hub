# 区分 chatbot、workflow、agent、multi-agent

## chatbot 聊天机器人

特征：单次或连续对话，无工具调用，无外部行动
工作模式：用户输入 → LLM 生成回复 → 返回结果
适用场景：FAQ 问答、情感陪伴、文本生成（翻译、摘要、创作）
局限：无法获取实时信息、无法操作系统、回答可能过时或幻觉
示例：GPT-3.5 纯对话、智能客服（无 API 调用的版本）

现在市面上的主流 AI 产品已经不再是单纯的 chatbot

```
2023年初：纯 Chatbot（只能对话）
    ↓
2023年中：+ 插件系统（可选工具调用）
    ↓
2024-2025：Agent 化（默认集成搜索、代码执行等）
    ↓
现在：Coding Agent（Claude Code、Codex 等，能操作代码库）
```

Function Calling、MCP 等协议让工具调用更稳定

纯 chatbot 现在只存在于：
早期版本或开源基础模型
特殊场景（如隐私要求极高、不允许联网的环境）

## workflow

特征：预定义流程，步骤固定，无自主决策
工作模式：输入 → 步骤 1 → 步骤 2 → 步骤 3 → 输出（流程硬编码）
适用场景：任务可预测、流程稳定、确定性高的场景
优势：可控、可追溯、成本低、适合生产环境
局限：无法处理异常情况、不能动态调整
示例：
固定模板的文档生成（填空式）
ETL 数据管道（extract → transform → load）
Anthropic 提到的"Prompt Chaining 模式"：prompt → LLM → 后处理

当任务可预测、流程稳定、普通脚本能解决时，agent 反而增加不确定性。直接用 workflow 比较好

### prompt Chaining 提示链

线性串行
固定步骤
gate 检查
仅 LLM
依赖对话历史
Stage 0 → Stage 1 → Stage 2 → Stage 3... 的数据传递，每个 Stage 的产出作为下一 Stage 的输入

```
prompt → LLM → 后处理（gate检查） → LLM → 后处理 → 输出
```

串行工作流，每个 LLM 调用处理前一步的输出（ 后一个 LLM 的输入依赖前一个 LLM 的输出结果，形成数据传递链。）
牺牲延迟换取更高准确率，通过让每次 LLM 调用变成更简单的任务。

```
步骤1: LLM 调用1
输入: "帮我写一段咖啡产品营销文案"
输出: "香醇咖啡，唤醒每一个清晨..."
                    ↓ (这个输出作为下一步的输入)
步骤2: LLM 调用2
输入: "将以下文案翻译成英文：香醇咖啡，唤醒每一个清晨..."
输出: "Aromatic coffee, awakening every morning..."
                    ↓
步骤3: LLM 调用3
输入: "检查翻译质量并优化：Aromatic coffee, awakening every morning..."
输出: "Premium aromatic coffee, awakening your every morning..."
```

- 公司的 ux-to-code 就是一种 Orchestrator-workers + Prompt Chaining 的混合模式（带状态管理的多模式混合编排系统，接近一个轻量级 Agent Harness）

## agent

特征：自主循环（observe → think → act），动态决策，工具调用
工作模式：

```
观察环境 → LLM 思考下一步 → 执行工具 → 观察结果 → 循环直到完成
```

核心能力：
工具选择（何时调用哪个工具）
错误处理（工具失败时的应对）
终止判断（什么时候停止循环）

适用场景：任务不可预测、需要多步探索、动态环境
关键设计：最大步数限制、超时控制、权限边界、trace 记录
示例：
Claude Code（读取代码库 → 分析 → 编辑文件 → 运行测试 → 修复）
Research Agent（搜索 → 筛选 → 总结 → 生成报告，带引用）

- 目前值得去查看的

  Coding Agents（Claude Code / Codex）- 真实代码库操作
  Agent Harness Engineering - 工具协议、权限、状态管理
  Personal Agents（OpenClaw / Hermes）- 长运行、记忆、skills

## Multi-Agent（多智能体）

特征：多个 agent 协作，角色分工，协调机制
工作模式：
Planner（规划）→ Executor（执行）→ Reviewer（审核）→ 循环改进

Supervisor（监督者）管理子 agent 任务分配

核心挑战：
职责边界（每个 agent 做什么）
循环/争论处理（避免死循环）
上下文膨胀（多轮对话导致信息过载）
任务漂移（目标偏离）

适用场景：复杂任务需要多视角、分工明确、可并行处理

关键原则：multi-agent 是协调问题，不是魔法；先做好单 agent，再考虑多 agent

示例：
研究系统：Researcher → Writer → Critic → Reviser
开发流程：Coder → Reviewer → Tester → Deployer

# agent 的基本循环

## 核心循环机制

```
observe → think → act → observe
观察环境 → LLM 思考下一步 → 执行工具 → 观察结果 → 循环直到完成
```

## 循环步骤详解

### 1. Observe（观察）

- **感知环境状态**：读取用户输入、工具执行结果、系统状态等信息
- **收集上下文**：获取所有可用的数据和环境信息
- **评估当前状态**：判断与目标的差距

### 2. Think（思考）

- **推理决策**：LLM 基于观察到的信息进行分析和规划
- **工具选择**：决定何时调用哪个工具、如何调用、参数是什么
- **策略调整**：根据历史执行结果优化下一步行动

### 3. Act（执行）

- **工具调用**：执行选定的操作（读取文件、运行命令、搜索代码、编辑文件等）
- **产生结果**：工具执行后生成新的输出或状态变化
- **记录行为**：trace 记录便于追溯和调试

### 4. Observe（再次观察）

- **获取执行结果**：读取上一步 Act 的产出
- **效果评估**：判断结果是否符合预期
- **终止判断**：任务完成、达到最大步数或超时时停止循环

## Agent 的核心能力

- **工具选择**：判断何时调用哪个工具
- **错误处理**：工具失败时如何应对和调整策略
- **终止判断**：什么时候停止循环（任务完成或达到限制）

## 关键设计要素

- **最大步数限制**：防止无限循环
- **超时控制**：避免任务执行时间过长
- **权限边界**：控制 Agent 能做什么操作
- **Trace 记录**：记录执行过程便于追溯和调试

## 实际示例：Claude Code

```
1. Observe: 读取代码库结构，理解用户需求
2. Think: 分析需要修改哪些文件
3. Act: 编辑文件内容
4. Observe: 运行测试查看结果
5. Think: 测试是否通过？需要修复什么？
6. Act: 修复问题
... 循环直到测试通过
```

## 总结

Agent 区别于传统 Chatbot 和 Workflow 的核心特征：**自主循环和动态决策能力**。

通过 observe→think→act 的循环机制，Agent 能够：

- 在动态环境中自主探索
- 根据实时反馈调整策略
- 处理复杂、不可预测的任务
